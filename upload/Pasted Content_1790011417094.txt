# 2. CRITICAL REGULATORY PRINCIPLE

Do NOT assume RFUND itself is a licensed deposit-taking institution, bank, microfinance bank, lender, payment institution, or investment manager.

The software must separate:

### RFUND technology/platform

from:

### Licensed financial/payment partners

The architecture must allow regulated activities to be performed by appropriately licensed partners where required.

Do not invent legal permissions.

Do not describe RFUND as a bank.

Do not represent customer balances as legally protected deposits unless the actual regulatory/partner structure supports that.

Implement configurable financial-provider abstractions so regulated financial services can later be connected to appropriate licensed institutions.

Create documentation describing regulatory assumptions and explicitly mark them as requiring legal/compliance confirmation.

# 3. NON-NEGOTIABLE ENGINEERING PRINCIPLES

## 3.1 Financial data is immutable

Never delete financial transactions.

Never directly modify historical ledger entries.

Corrections must happen through:

* reversal
* adjustment
* correction transaction
* compensating ledger entry

Every correction must record:

* actor
* timestamp
* reason
* original transaction
* corrective transaction
* authorization

---

## 3.2 Never calculate financial balances by blindly incrementing a database field

Do NOT implement:

```python
account.balance += amount
```

as the authoritative financial mechanism.

Balances must derive from the ledger or a carefully maintained ledger-backed balance projection.

The ledger is authoritative.

---

## 3.3 Double-entry accounting

Every posted financial transaction must satisfy:

```text
TOTAL DEBITS = TOTAL CREDITS
```

The system must reject any transaction that violates this invariant.

Use decimal monetary arithmetic.

Never use floating point for money.

Use:

```python
Decimal
```

and PostgreSQL numeric/decimal fields.

---

## 3.4 Currency

Initial currency:

```text
NGN
```

Design the monetary system so additional currencies can eventually be supported.

Every money amount must have an explicit currency.

---

## 3.5 Idempotency

Every externally initiated financial operation must support idempotency.

This applies to:

* Paystack webhooks
* payment initialization
* payment verification
* transfers
* payouts
* loan disbursement
* repayment
* agent cash transactions
* scheduled jobs
* notification jobs

Repeated requests must not create duplicate financial effects.

---

## 3.6 State machines

Financial objects must have explicit states.

Do not implement workflows using random Boolean fields.

Examples:

```text
PENDING
PROCESSING
SUCCESS
FAILED
REVERSED
CANCELLED
SETTLED
```

Loan:

```text
DRAFT
SUBMITTED
UNDER_REVIEW
VERIFICATION_REQUIRED
APPROVED
OFFERED
ACCEPTED
DISBURSEMENT_PENDING
DISBURSED
ACTIVE
DELINQUENT
DEFAULTED
RESTRUCTURED
COMPLETED
REJECTED
CANCELLED
```

KYC:

```text
NOT_STARTED
PENDING
UNDER_REVIEW
VERIFIED
REJECTED
EXPIRED
```
